# PR #12: исправления security review

Ветка: `feature/v2.5-storage-location-foundation`.
Коммит исправлений: `efe96bd94e532b2b716af3495b0a87a23481bba7` (включает `8bf3e44` и `53383ef`).
Существующий PR: https://github.com/seo79-sec/password-saver/pull/12

## P0 — legacy-папка с EXE

Инвентаризация разделена на legacy и managed. Legacy проверяет только известные
vault-файлы; EXE, checksum и другие пользовательские файлы не читает, не меняет и
не копирует. AppData/staging сохраняют строгий allowlist. Проверки абсолютного
пути, размеров, обычного типа файла, symlink/reparse points не ослаблены.

## P1 — совместимость со старым рабочим каталогом

Добавлен нативный выбор папки Wails без аргумента пути из JavaScript. Backend
выдаёт краткоживущий capability только для выбранной папки. Строгая проверка
селектора, аутентификация паролем/TOTP и отдельный токен подтверждения копирования
используют существующую схему миграции. Назначение фиксировано в AppData;
непустой target и конкурирующие legacy-наборы блокируют перенос.

CWD автоматически не выбирается. В UI есть подсказка для старой рабочей папки и
явное подтверждение создания отдельного пустого vault. Backend блокирует
создание во время выбора/подготовки переноса. Logout, отмена, истечение токена и
запоздалый ответ диалога не возвращают разрешение или чувствительное состояние.

## P2 — стоимость определения расположения

Обычные route/status/save-проверки используют файловые метаданные; активный
контейнер не перечитывается ради вычисления каталога. Полная ограниченная
инвентаризация остаётся для аутентификации и побайтовой сверки копирования.

Консервативное исключение: при наличии AppData, legacy рядом с EXE и квитанции
сохраняется полная сверка хешей legacy. Без неё подмена с теми же размером/mtime
могла бы остаться незаметной. Кэша доверия по этим метаданным нет. Если квитанции
нет, возвращается конфликт без чтения payload. Содержимое активного target
при проверке квитанции не читается.

## Дополнительный аудит

Исправлено пустое поле флагов ACE в Windows SDDL для файлов (`A;;FA`); добавлен
Windows runtime-тест ACL. Он сравнивает значения SID через Windows API,
права доступа и флаги наследования; текстовые алиасы SDDL (`LA` на CI worker)
не влияют на результат. Квитанция читается с ограничением размера и сверкой
идентичности открытого файла. Подтверждение переноса также блокируется при сессии
восстановления. Проверены существующие пути v1/v2, backup, selector, TOTP и
атомарная публикация; production-вызовов `vaultPaths(".")`/`os.Chdir` нет.

## Дополнение P1: остатки прерванного сохранения

### Причина и исправленные функции

Строгий allowlist managed-каталога ранее отклонял остатки `.vault-write-*` и
`.vault-v2-stage-*`, которые остаются при завершении процесса до выполнения defer.
Это блокировало доступ даже к исправному основному контейнеру.

- `storage_inventory.go`: `scanVaultDirectoryDetails`, `isVaultWriteTemporary`,
  metadata-only подсчёт с проверкой типа, размера, symlink/reparse и точного имени.
- `storage_location.go`: `discoverStorageRouteWithSource`, `storageLocationStatus`,
  `activeVaultStorageDirectory`, `ensureStorageScaffold`: диагностика, запрет
  создания при одних остатках, отсутствие операций с содержимым/ACL по temp-пути.
- `v2_setup.go`: `CreateV2Vault` повторяет проверку остатков под write locks.
- `app.go`: `updateVault` закрывает v1-сессию при потере обычных контейнеров с
  сохранением только residue; v2 сохраняет существующий fail-closed путь сессии.
- `v2_wails.go`: `OpenStorageFolder` допускает только открытие фиксированной
  безопасной папки для ручного анализа, включая небезопасный дочерний объект.
- `frontend/src/App.svelte`, `frontend/src/security.js`,
  `frontend/src/security.test.js`, `frontend/wailsjs/go/models.ts`: предупреждение,
  заблокированные диагностические состояния и дополнительные поля статуса.
- `storage_residue_test.go`, `storage_selection_windows_test.go`: регрессии.
- `docs/STORAGE_WRITE_RESIDUE.md`, `docs/V2_5_STORAGE_ARCHITECTURE.md`,
  `docs/WINDOWS_STORAGE_MIGRATION_TEST_PLAN.md`, этот отчёт: политика и ручной план.

Новый Wails-метод не нужен: существующий `GetStorageLocationStatus` возвращает
только число временных файлов и категорию проблемы дополнительно к прежним полям.
Содержимое файлов, имена, новые полные пути и подробности ошибок ОС не раскрываются.

### Политика

Только точные префиксы с каноническим десятичным uint32-суффиксом текущего Go,
обычный файл без symlink/reparse и размер 0..max(v1 file limit, v2 container limit).
Это не доказательство происхождения: содержимое остаётся недоверенным и не читается.
Временные файлы не входят в container inventory, не выбираются как primary/backup,
не копируются и не удаляются. Существующие selector, AEAD, мастер-пароль, TOTP,
проверки ревизий и явное восстановление `.bak` остаются обязательными.

При исправном vault доступен вход с предупреждением. При повреждённом/отсутствующем
primary и корректной backup/selector доступно прежнее двухэтапное recovery с
диагностическим архивом. Только остатки без штатных контейнеров дают
`incomplete-write` и блокируют вход/создание. Подозрительные объекты дают отказ.
Непустое назначение переноса не заменяется. Автоматической очистки не добавлено.

Аудит других CreateTemp/MkdirTemp и точные пределы:
[STORAGE_WRITE_RESIDUE.md](STORAGE_WRITE_RESIDUE.md).

### Ограничения и ручная проверка

Windows GUI в облачной Linux-среде не запускался. Добавлены десять ручных сценариев
с искусственными остатками, TOTP, backup/recovery, повторной записью и reparse.
