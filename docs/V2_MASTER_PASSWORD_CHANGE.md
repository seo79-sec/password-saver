# Смена мастер-пароля v2

В разблокированном хранилище откройте «Настройки» → «Безопасность аккаунта» →
«Изменить мастер-пароль». Введите текущий пароль, новый пароль из 12 или более
символов, его подтверждение и текущий код TOTP, если двухфакторная аутентификация
включена. Для хранилища v1 сначала выполните явную миграцию во вкладке «Хранилища».

При успехе PasswordSaver закрывает текущую сессию. Войдите с новым паролем и
пройдите обычную проверку TOTP. Штатная `.bak` обновляется до **текущего** состояния
хранилища, поэтому предыдущая версия записей в `.bak` больше не хранится.
Последующие изменения снова сохраняют предыдущую ревизию в `.bak`.

## Протокол записи

1. Go требует активную v2-сессию с пройденной 2FA, если она включена. Порядок
   блокировок совпадает с CRUD: `App.mu`, mutex сессии, mutex активации, mutex
   файлов v2. Это сериализует операцию с Logout, автоблокировкой и восстановлением
   внутри процесса. Дедлайн автоблокировки проверяется перед первой заменой.
2. Проверяются путь, действующий селектор, отпечаток основного контейнера из
   сессии и снимок штатной резервной копии. Движок полностью аутентифицирует
   исходный контейнер текущим паролем, меняет соль, KEK и обёртку прежнего DEK.
   TOTP проверяется повторно в обычном временном окне, с общим счётчиком
   попыток. Число попыток не сбрасывается проверкой одного лишь пароля.
3. Go открывает новый контейнер новым паролем до любых замен файлов. Payload,
   его nonce, формат и алгоритмы остаются прежними. Временный буфер plaintext
   очищается по модели best effort.
4. Байты проверенного контейнера записываются во временный файл в защищённом
   каталоге и синхронизируются. Сначала атомарно заменяется `vault_data.v2.enc.bak`.
   После её синхронизации и сверки таким же способом заменяется
   `vault_data.v2.enc`. Перед каждой заменой снова проверяются расположение,
   селектор и ожидаемые снимки обоих файлов. Перед подтверждением успеха оба
   файла читаются и сверяются с подготовленным контейнером. Селектор сохраняется.
5. Сессия закрывается после успеха и после любой ошибки на этапе сохранения.
   Если замена могла состояться, интерфейс сообщает, что результат не
   подтверждён. Когда файлы доступны, сообщение показывает какие снимки были
   прочитаны. Оно описывает видимые байты, а не обещает, что они переживут сбой.

Обе записи выполняются независимо. Unix использует rename и синхронизацию
каталога. Windows использует MoveFileEx с WRITE_THROUGH для файла в том же
каталоге. Поддержка атомарной замены отдельного файла зависит от файловой
системы. Двухфайловой транзакции нет.

| Точка сбоя | Наблюдаемое состояние при поддерживаемой замене | Действие после перезапуска |
| --- | --- | --- |
| До замены `.bak` | Основной файл и `.bak` в состоянии до операции | Обычный вход со старым паролем. |
| После замены `.bak`, до замены основного файла | Основной файл открывается старым паролем. `.bak` содержит те же последние данные под новым паролем. | Для завершения смены введите новый пароль на экране входа и выберите «Восстановить из резервной копии v2». Проверьте окно подтверждения, подтвердите и пройдите TOTP, если включён. Если решили прервать смену, можно войти со старым паролем в текущий основной файл. Последующее обычное сохранение снова обновит `.bak` в соответствии с основным файлом. |
| После обеих замен | Основной файл и `.bak` открываются новым паролем. При сбое подтверждения записи они перепроверяются при входе. | Войдите с новым паролем. TOTP остаётся включён, если он был включён до смены. |
| Файлы недоступны или изменены внешним процессом | Снимки могут не соответствовать ни одной из ожидаемых ревизий | Сохраните копии файлов для диагностики, выясните состояние каталога и используйте обычное восстановление только для успешно аутентифицированной `.bak`. |

При неизвестном результате сначала проверьте вход с новым паролем. Если новый
пароль открывает только `.bak`, выберите явное восстановление **до**
редактирования записей. Восстановление сохраняет недоступный по этому паролю
основной файл как диагностический архив. Архив может содержать прежнюю обёртку.
Штатное восстановление читает только `.bak`, никогда не выбирает архивы или
временные файлы. Временные файлы этой операции содержат только новый контейнер.

## Модель угроз

Смена прекращает работу старого пароля для обычного открытия новых основного
файла и `.bak`. Она не отзывает ранее сделанные копии, включая диагностические
архивы. Старый пароль может открывать такие копии. Поскольку DEK сохраняется,
тот, кто уже получил DEK или может извлечь его из старой копии с известным ему
паролем, может расшифровать данные, которые всё ещё используют этот DEK.
Смена пароля не является ротацией DEK при его компрометации.

Подмена каталога, селектора и файлов проверяется перед заменами. Эта проверка не
является атомарным compare-and-swap для внешних процессов. Не запускайте два
экземпляра, которые записывают в одно хранилище одновременно. Процесс с полным
контролем файлов может подменять или откатывать и контейнер, и селектор. Go и
JavaScript не гарантируют физическое стирание каждой копии строки из RAM.

## Ручная проверка Windows

Используйте отдельный профиль Windows, WebView2 и только синтетические данные.
Запишите номер коммита из README артефакта и версию Windows/WebView2.

1. Создайте v2, добавьте несколько записей, измените пароль без TOTP. Проверьте
   скрытие трёх полей, отмену и очищение формы, новый вход и отказ со старым
   паролем. Повторите после закрытия и запуска EXE.
2. Включите TOTP и повторите смену с неправильным, просроченным и правильным
   кодом. Проверьте пять ошибок и временную блокировку. Войдите с новым паролем
   и убедитесь, что доступ к записям появляется только после TOTP.
3. Добавьте запись после смены. В тестовой папке сохраните копию основного
   файла и повредите его. Убедитесь, что `.bak` восстанавливает предыдущую
   ревизию с новым паролем, а старый пароль отвергается и для восстановления.
4. Для проверки прерывания на копии тестового хранилища подготовьте смешанное
   состояние: сохраните первичный файл до смены, завершите смену, закройте
   программу и верните старый первичный файл, оставив новую `.bak`. Запустите
   EXE, проверьте вход с новым паролем через отдельное подтверждение восстановления
   и сохранность записей, TOTP, диагностического архива и селектора. Отдельно
   проверьте сбой записи на тестовой машине, удерживая основной файл без права
   совместного удаления и освобождая его для повторного входа.
5. Проверьте Light/Dark/System, Escape, двойное подтверждение, автоблокировку
   с открытым диалогом и отсутствие старых полей после повторного входа.

Успешный Windows Wails build проверяет сборку. Перечисленные действия
относятся к ручному запуску EXE.
