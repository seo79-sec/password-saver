# PR #12: ручная проверка Windows EXE

Статус: сценарий подготовлен; запуск GUI в облачной Linux-среде не выполнен.
Успешные Go tests и Windows Wails build не доказывают работу нативного диалога,
WebView2 и всех политик доступа на пользовательских Windows.

## Изолированный стенд

Использовать отдельную Windows VM/тестовую учётную запись с WebView2, пустым
тестовым AppData и синтетическими данными. Не переименовывать, не удалять и не
перезаписывать каталог PasswordSaver основного пользователя. Для каждого
сценария возвращать снимок тестовой VM либо использовать новый тестовый профиль.

- Сборка PR #12 из проверяемого commit (зафиксировать SHA и SHA-256 EXE).
- Неизменённый EXE релиза 2.0.0 для воспроизведения старых способов запуска.
- Отдельные папки `C:\PS-Test\Application`, `C:\PS-Test\WorkingVault` и,
  если доступен отдельный тестовый диск, `D:\PS-Test\Vault`.
- Синтетический мастер-пароль, несколько вымышленных записей и тестовый TOTP.
- Исходный v1 fixture — только с синтетическими данными. Для v2 создать набор
  через 2.0.0, добавив минимум две записи, чтобы появилась `.bak`.

Перед переносом записать SHA-256 **всех** файлов источника через `Get-FileHash`,
включая EXE, checksum и произвольный `notes.txt`. Записать их ACL через `icacls`.
После каждой отмены/ошибки и успешного переноса сравнить байты и ACL источника.
Проверять только тестовый `%LOCALAPPDATA%\PasswordSaver\vaults\default`.

## Что приложить к повторному security review

- Версия Windows, тип ФС, версия WebView2, SHA commit и хеш EXE.
- Результат каждого сценария; отдельно отметить реальные второй диск, shortcut,
  Controlled Folder Access/корпоративный профиль, если они проверялись.
- Сравнение исходных SHA-256/ACL и ожидаемых target-файлов, без паролей и TOTP-секретов.
- Наблюдения при отказах и повторном запуске. Не заявлять гарантированную
  устойчивость к потере питания: на Windows используются существующие
  file-sync + `MoveFileEx(...WRITE_THROUGH)`, без переносимой гарантии fsync каталога.

Тестовая буква диска в Windows CI проверяет абсолютные пути и копирование между
разными drive letters. Она не заменяет ручную проверку отдельного физического
диска, съёмного носителя или сетевой файловой системы.


## P1: остатки после прерванного сохранения

Выполнять только в изолированном тестовом профиле/VM. Перед действиями закрыть
приложение, снять snapshot VM и записать SHA-256 primary, backup, selector, v1
и его backup. Не делать искусственных сбоев с настоящим хранилищем.

1. В managed-каталоге тестового профиля рядом с исправными v2 primary/backup/selector
   создать обычный `.vault-write-123456` с синтетическими байтами. Запустить EXE,
   проверить предупреждение и «Открыть папку хранилища», вход и TOTP. До изменения
   записей все исходные SHA-256 должны совпасть. Служебный файл не удалён.
2. Повторить с `.vault-v2-stage-123456`, затем с обоими файлами. Добавить/изменить
   вымышленную запись, проверить новый backup, закрыть/запустить EXE и снова войти.
   Остатки не изменились; legacy-источник также не меняется.
3. Повторить вход, TOTP и сохранение для синтетического v1 в AppData с остатком.
   Файл другого префикса не должен переключить формат на v2.
4. Повредить только тестовый v2 primary при исправной backup. Добавить остаток.
   Проверить отдельную подготовку/подтверждение recovery; до подтверждения primary
   не меняется, после него повреждённые байты сохранены в архиве, backup, selector,
   файлы v1 и остаток не меняются. TOTP обязателен согласно восстановленному vault.
5. Удалить только тестовый primary, оставив backup/selector/остаток; проверить то
   же явное восстановление без автоматического выбора временного файла.
6. В новом тестовом профиле оставить только `.vault-v2-stage-123456`. Проверить
   диагностическое состояние, недоступность создания пустого vault и возможность
   открыть папку для сохранения её копии. Никакой файл не активируется. Повторить
   с оставшимся selector, но без primary/backup.
7. Проверить пустой допустимый остаток (прерванное создание) и неправильные имена:
   `.vault-write-`, `.vault-write-01`, `.vault-write-123.txt`, неизвестный файл.
   Неверные имена блокируют операции. Проверить oversized synthetic sparse file
   выше предела из STORAGE_WRITE_RESIDUE.md: отказ, без чтения и удаления.
8. Создать в VM symlink/junction/reparse с подходящим временным именем и каталог
   вместо файла. Проверить понятную диагностику, отказ во входе/записи и сохранность
   объектов/цели ссылки. При ссылке вместо самого managed-каталога даже открытие
   папки должно быть отклонено. Не переходить по подозрительным ссылкам вручную.
9. В тестовом процессе прервать большую запись до публикации (с отладчиком или
   fault-injection тестовой сборки). После перезапуска проверить вход в последний
   корректный primary либо штатный recovery из backup; не переименовывать остатки.
   Повторить для первичного создания: только остаток не должен разрешать новый vault.
10. Сравнить SHA-256 остаточных файлов после всех отказов/входов/восстановлений.
    Автоматического удаления или замены их содержимого быть не должно. Сохранить
    копию всей тестовой папки для анализа, не отправляя пароли и TOTP-секреты.

Зафиксировать сборку/commit, версию Windows/WebView2, результаты каждого сценария
и какие реальные сбои были воспроизведены. Эти действия подготовлены, но Windows
GUI в облачной Linux-среде не запускался. Автотест с завершением дочернего процесса
не заменяет испытание потери питания.
