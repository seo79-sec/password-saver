# PasswordSaver 2.5-A: локальное расположение хранилища

## Цель и совместимость

Новые пользовательские файлы находятся отдельно от установленного приложения:

```text
%LOCALAPPDATA%/PasswordSaver/
├── vaults/
│   └── default/
│       ├── vault_data.v2.enc
│       ├── vault_data.v2.enc.bak
│       ├── vault_format.state
│       └── storage.migration.json   # только после явного копирования
├── backups/                         # зарезервировано
└── config/                          # зарезервировано
```

В Windows базовый каталог берётся из `LOCALAPPDATA` (при отсутствии значения
используется `os.UserCacheDir`). В других ОС используется каталог настроек
пользователя. Путь формируется централизованно, нормализуется и проверяется
как абсолютный. `password-saver.exe`, его контрольная сумма и файлы релиза не
перемещаются. Backend операции создания, входа, CRUD, TOTP, записи, выбора
формата, резервного восстановления и миграции v1→v2 используют этот путь.
Production-код не меняет current working directory и не выбирает его
автоматически. Если версия 2.0.0 сохраняла файлы в рабочую папку ярлыка,
пользователь может явно выбрать эту папку через системный диалог.

Контейнеры v1 и v2 копируются байт в байт. Формат v2, AES-256-GCM, Argon2id,
DEK/KEK и селектор формата не меняются. Кузнечик-MGM не добавляется.

## Разрешение расположения

При запуске выполняется read-only инвентаризация известных зашифрованных
файлов в AppData и рядом с исполняемым файлом старой установки. Произвольный
рабочий каталог процесса не сканируется.

| Состояние | Поведение |
| --- | --- |
| Нет известных файлов | создаётся стандартный каталог; доступно создание нового v2 |
| Только AppData | AppData становится активным расположением |
| Только старый каталог | вход и создание заблокированы до явного переноса |
| Данные в обоих местах | конфликт; приложение ничего не выбирает и не перезаписывает |
| Посторонние файлы рядом с EXE или в выбранной legacy-папке | игнорируются, не читаются и не копируются |
| Непредвиденный файл в AppData/staging; symlink/reparse point в пути или на месте известного vault-файла | операция останавливается |

`scanVaultDirectory` имеет два явных режима. Legacy-режим обращается только к
фиксированным именам v1/v2 primary, их `.bak` и `vault_format.state`; не читает
EXE, checksum, пользовательские документы и не перечисляет посторонние записи.
Отсутствие vault-файлов допустимо. Известные файлы проверяются независимо от
содержимого, в том числе пустые и повреждённые: тип, предел размера,
symlink/reparse point, безопасные компоненты пути.

Managed-режим для AppData и staging сохраняет строгий allowlist. Кроме известных
vault-файлов допускаются проверенные по метаданным остатки штатной записи
(они не читаются/не удаляются), ограниченная по размеру квитанция переноса и обычные
диагностические архивы повреждённых контейнеров. Неожиданные объекты приводят к
отказу. При копировании требуются отсутствующий или **пустой** AppData destination;
существующее содержимое не очищается. Диагностические архивы остаются у источника
и не включаются в перенос.

Если успешная миграция оставляет старый каталог нетронутым, рядом с целевой
копией сохраняется `storage.migration.json`. В нём записаны путь источника и
SHA-256 хеши исходных зашифрованных файлов. Это позволяет узнавать завершённое
явное копирование, даже если пользователь позднее изменил уже активный AppData
контейнер. Если старый каталог изменился после копирования, приложение снова
показывает конфликт. Квитанция нужна для учета завершённой операции и не
является криптографической границей безопасности: пользователь или процесс с
прямым доступом к файлам может изменить квитанцию, контейнер и селектор.

## Старые рабочие каталоги и Wails API

На экране входа есть «Не нашли своё хранилище? Указать расположение вручную».
Это необходимо для совместимости с 2.0.0, которая использовала рабочий каталог
процесса, включая поле «Рабочая папка» Windows-ярлыка и другие диски.

- `SelectLegacyStorageDirectory()` не принимает строку пути из JavaScript.
  Открывается нативный диалог Wails. Отмена ничего не переносит.
- Backend проверяет абсолютный путь, компоненты, все известные файлы и строгий
  селектор. Неизвестный/противоречивый селектор и v2 без селектора отвергаются.
- Возвращаются только путь для отображения, фиксированное назначение AppData и
  случайный токен выбранной папки на две минуты. Ни содержимое файлов, ни ключи
  frontend не получает. В Wails нет универсального API чтения/записи по пути.
- `PrepareSelectedStorageLocationMigration(token, password, totp)` принимает
  этот токен, проверяет пароль/TOTP существующим механизмом и подготавливает
  отдельный одноразовый токен копирования. Подготовка не является согласием на
  запись: требуется ещё `ConfirmStorageLocationMigration(copyToken)`.
- Выбор другой папки не обходит конфликт: непустой AppData или два различных
  обнаруженных legacy-источника запрещают перенос. Ручной выбор не разрешает
  перезапись даже при наличии квитанции предыдущего переноса.
- Сессии v1/v2, ожидание TOTP и незавершённое восстановление блокируют перенос.
  Выбор папки/ожидание подтверждения блокируют создание второго пустого vault.
- Logout, отмена и истечение срока очищают capability. Потеря процесса не оставляет
  долговечного разрешения: папку выбирают и аутентифицируют заново. Поколение
  backend-состояния не позволяет результату диалога после Logout вернуть выбор.
  Frontend также игнорирует запоздалые ответы, отменяет выданные ими токены при
  закрытии окна/Logout/unmount и очищает пароль и код TOTP.

Рабочий каталог не сканируется автоматически. Экран создания нового vault
содержит предложение найти старый и отдельный флажок осознанного создания пустого.
Приложение не может доказать отсутствие старых файлов во всех каталогах/дисках.
Ручной источник используется только для ограниченного переноса; его путь не
становится новым активным расположением. После успешного копирования всегда
используется стандартный AppData.

## Быстрые и полные проверки

Обычное определение каталога (`discoverStorageRoute`, `activeVaultStorageDirectory`)
проверяет абсолютные пути и файловые метаданные. Для статуса читается только
маленький селектор. Содержимое активных primary/backup не загружается заново
ради вычисления пути; проверки аутентификации и ревизии в самих операциях
входа, сохранения и восстановления сохраняются.

Полные ограниченные чтения нужны для подготовки, повторной проверки источника,
побайтовой сверки staging и аутентификации. Есть намеренное исключение: когда
AppData и обнаруженный рядом с EXE legacy-каталог одновременно содержат vault,
квитанцию нельзя подтвердить только по размеру/mtime. Поэтому маршрут полностью
пересчитывает хеши legacy-источника; активный контейнер для этого не читается.
Без квитанции сразу возвращается конфликт. Кэш решения по метаданным отсутствует.
Это сохраняет обнаружение изменения legacy-файлов, даже если их размер/mtime
восстановлены. На больших сохранившихся legacy-копиях это по-прежнему дополнительный
дисковый ввод; сохранность данных имеет приоритет. Произвольно выбранные папки
после завершения копирования не обходятся фоновым сканированием.

## Двухэтапное копирование

1. Пользователь выбирает перенос, пока хранилище полностью заблокировано.
   Открытая v1/v2 сессия, включая ожидание TOTP, не допускается.
2. Пользователь вводит мастер-пароль и TOTP, если он включён. Проверяется
   строгий селектор и аутентифицируется активный контейнер. Для `v1-prepared`
   проверяются обе версии, соответствие хешей селектора и равенство расшифрованных
   данных. При повреждённом или отсутствующем primary разрешается продолжить
   только если соответствующая зашифрованная резервная копия аутентифицируется.
   Неподдерживаемый v2 формат не трактуется как повреждённый и не заменяется
   старой копией.
3. Успешная подготовка создаёт краткоживущий одноразовый токен и хранит в RAM только
   снимок зашифрованных файлов. Он не изменяет дисковые данные.
4. После отдельного подтверждения создаётся временный каталог рядом с целевым.
   Копируются известные зашифрованные файлы и селектор. Оригиналы остаются
   нетронутыми. Проверяются актуальность снимка источника, точное побайтовое
   равенство staging-копии, размеры и типы файлов.
5. Файлы синхронизируются, затем staging-каталог атомарно публикуется
   no-replace перемещением в `vaults/default`. Перезапись существующего
   назначения запрещена. При ошибке staging удаляется только созданный этой
   операцией каталог; исходный набор остаётся на месте.
6. После переноса обычный механизм входа открывает файл из AppData. Формат
   v1 остаётся доступным для чтения и существующей явной миграции v1→v2.
   Копирование расположения само по себе не активирует другой формат и не
   удаляет v1.

Если основной контейнер не проходит проверку, но backup аутентифицирован,
перенос сохраняет оба файла без изменений. Это не выполняет восстановление:
после переноса пользователь должен запустить отдельную подтверждаемую
процедуру восстановления. В частности, при восстановлении backup, созданной
до включения TOTP, TOTP вернётся к состоянию внутри этой backup. Это свойство
контейнера, а не особенность копирования.

Сбой до атомарного перемещения оставляет старые файлы активными; незавершённый
staging-каталог не выбирается автоматически. Повторная подготовка создаёт новый
staging-каталог. Сбой синхронизации родительского каталога после перемещения
возвращает неопределённость долговечности, но не удаляет ни источник, ни уже
опубликованную целевую копию. При следующем запуске наличие валидной квитанции
позволяет распознать этот результат.

## Файловая система и ограничения угрозомодели

- Перед чтением проверяются абсолютные пути, компоненты каталогов, тип файлов,
  reparse points/symlinks и верхние пределы размера. Открытый файл сверяется
  с предварительным `Lstat`; файловые операции работают с ограниченным размером.
- В Unix-каталогах применяются права `0700`, к файлам — `0600`.
- В Windows DACL для создаваемых/используемых каталогов и файлов ограничивается
  текущим пользователем, `SYSTEM` и локальными администраторами. При невозможности
  применить security descriptor приложение останавливает операцию. В SDDL
  явно сохраняется пустое поле флагов ACE для файлов (`A;;FA`); для каталогов
  используются `OICI`. Обе формы выполняются в Windows unit-тесте. Родительский
  `%LOCALAPPDATA%` не меняется. Проверка ручной Windows ACL обязательна для
  поддерживаемых версий Windows и корпоративных профилей.
- На Linux используется `renameat2(RENAME_NOREPLACE)`. На Windows используется
  `MoveFileEx` без флага замены и с `MOVEFILE_WRITE_THROUGH`. Платформы без
  подтверждённого атомарного no-replace перемещения отказывают в миграции.
- Windows API не предоставляет через текущую абстракцию переносимую гарантию
  fsync каталога; атомарное перемещение запрашивает write-through, а ошибки
  файлов и закрытия проверяются. Отказ подтверждения синхронизации каталога
  сообщается как неопределённый commit.
- Блокировки синхронизируют операции одного процесса. Они не защищают от
  процесса с теми же правами, который непосредственно заменяет файлы между
  проверками. Ни квитанция, ни селектор не защищают от полного локального
  контроля над файловой системой или отката целой папки.
- На Windows сетевой каталог, перемещаемый диск, политики Controlled Folder
  Access и нестандартные ACL могут запрещать создание или синхронизацию. В этом
  случае приложение сообщает об ошибке и оставляет исходные данные.
- Временный snapshot содержит только ciphertext и селектор; открытые пароли,
  мастер-пароль и ключи в него не записываются. Очистка ciphertext-среза в RAM
  выполняется при отмене, ошибке, выходе и истечении токена, но Go не обещает
  уничтожить все копии из памяти процесса.

## Проверки Windows вручную

Использовать только синтетические учётные данные, а не настоящие пароли.

1. Установить тестовую сборку в отдельную папку, запустить впервые и проверить,
   что создание v2 пишет файлы только под `%LOCALAPPDATA%\PasswordSaver\`.
2. Добавить синтетические записи, закрыть и вновь открыть приложение. Убедиться,
   что вход, TOTP, CRUD и backup работают из AppData.
3. Запустить приложение из другой рабочей папки и затем переместить только exe.
   Убедиться, что активный AppData vault остаётся тем же.
4. Подготовить копию v1 и копию v2 рядом с тестовым exe. Проверить распознавание,
   отмену первого шага, ошибочный пароль/TOTP, отмену второго шага, истечение
   токена и повторную подготовку. Убедиться, что исходные bytes и хеши не
   изменились.
5. Подтвердить копирование. Сравнить SHA-256 каждого известного исходного и
   AppData файла. Убедиться, что после первого входа последующие записи меняют
   только AppData; старый каталог остаётся исходной копией.
6. Создать разные хранилища в старой папке и AppData. Проверить, что вход и
   создание заблокированы, обе папки можно открыть, байты не изменены.
7. Повредить только синтетический primary, оставив корректный backup. Перенести
   набор, затем отдельно восстановить backup. Проверить диагностический архив,
   TOTP-состояние из backup и сохранность legacy-файлов.
8. Проверить NTFS ACL на `PasswordSaver`, `vaults`, `default`, `backups`,
   `config`, контейнерах, резервных копиях и селекторе: полный доступ у текущего
   пользователя, системной учётной записи и администраторов; отсутствие доступа
   у обычной группы `Users`.
9. Проверить сценарии отказа: назначение занято, диск заполнен/доступ запрещён,
   каталог назначения заменён reparse point, окно закрыто во время большой
   копии, процесс завершён до публикации staging-каталога.
10. После каждого отказа снова открыть старое хранилище и убедиться, что источник
    не был удалён или перезаписан.


## Дополнительный аудит PR #12

- В production Go-коде нет `vaultPaths(".")`, `os.Chdir` и операций по относительным
  константам vault. Wails-обёртки разрешают AppData, внутренние функции принимают
  явные пути для тестов/контролируемой миграции.
- v1/v2 сохранение, `.bak`, reset/recovery, селектор и TOTP продолжают использовать
  существующие реализации. Расположение не меняет криптографические форматы.
- Backend подтверждения повторно проверяет отсутствие сессии, включая сессию
  восстановления. Счётчик TOTP не обнуляется неверным паролем/кодом или Logout.
- Смена источника либо появление файлов назначения до подтверждения прерывают
  перенос. Изменение источника во время staging также обнаруживается.
- Ошибка синхронизации до публикации не публикует target; после публикации
  возвращается неопределённый commit с сохранением обеих копий. На Windows
  ограничение гарантии directory fsync остаётся таким, как описано выше.
- Квитанция читается с ограничением размера и проверкой идентичности открытого
  файла. Никаких новых автоматических удалений legacy не добавлено.
- CI выполняет `go test ./...` и на Windows, чтобы реально проверить SDDL/ACL,
  reparse points, no-replace move и путь на другом диске (тестовая буква диска,
  сопоставленная только временному каталогу). Это дополняет Wails build, но не
  заменяет ручной запуск EXE/WebView2.

Расширенный сценарий настоящего Windows EXE:
[WINDOWS_STORAGE_MIGRATION_TEST_PLAN.md](WINDOWS_STORAGE_MIGRATION_TEST_PLAN.md).


## Остатки прерванных записей

Служебные файлы штатных writer-функций имеют отдельную строгую политику:
[STORAGE_WRITE_RESIDUE.md](STORAGE_WRITE_RESIDUE.md). Допустимые остатки не
блокируют вход или явное backup-recovery, не становятся активными и не копируются.
Только остатки без контейнера/backup дают диагностическое состояние, запрещающее
создание нового vault. Непустой target переноса по-прежнему не заменяется.
